# План реализации ARCHWALK для Cursor

Этот документ передаётся исполнителям вместе со всем пакетом. Результатом их работы должен стать устанавливаемый плагин для проверенной сборки Rhino 8.25, а не только библиотека математики или демонстрация с движущейся камерой. На этапе подготовки данного пакета код плагина не создавался.

## 1 Инструкция для первого агента

Ниже текст задания, который можно передать агенту целиком.

> Реализуй плагин ARCHWALK для Rhino 8.25 по этому пакету. Сначала прочитай 00_START_HERE.md и все документы 01–06. Составь карту требований и проверь локальную среду Rhino, SDK и .NET. Не заменяй поведение продукта упрощёнными догадками.
>
> Начни с технических проверок P0: безопасный FPS-ввод, независимое превью, обратимая камера, сохранение наблюдателей и Undo. Для каждой покажи результат запуска именно в Rhino 8.25 и ограничение, если оно обнаружено. Онлайн-справка актуального RhinoCommon не доказывает наличие нового API в этой версии.
>
> Затем последовательно реализуй этапы P1–P5. После каждого этапа выполни относящиеся к нему проверки из 05_ACCEPTANCE_TESTS.md. Держи математику отдельно от Rhino и Windows. Не меняй глобальные алиасы, настройки навигации, геометрию, слои, CPlane и единицы модели ради управления камерой.
>
> Все числовые значения и клавиши бери из 02_CAMERA_AND_MOVEMENT.md. Не выбрасывай живое превью, русский WASD, безопасный выход или следование полу из объёма полной v1, если их реализация сложнее ожидаемого. Предлагай конкретное исправление архитектуры с доказательством технического ограничения. Не объявляй неподтверждённые тесты выполненными.
>
> Если в текущей среде нет Windows Rhino 8.25, можно подготовить код и тесты независимого ядра, но host-проверки остаются явно невыполненными. Организуй запуск на доступном целевом компьютере; не подменяй этот этап тестированием только на Rhino 9 или выводом успешной компиляции.
>
> Финальная поставка: исходники, воспроизводимая сборка, .rhp, локальный пакет .yak для Windows, инструкция установки и удаления, таблица управления и отчёт по приёмочным тестам. Публично ничего не публикуй. Не добавляй VR, маршруты, рекламу, облако, лицензирование, аналитику или игровой движок.

## 2 P0 Технические доказательства

До большого интерфейса выполнить пять ограниченных проверок. Их код в дальнейшем либо становится проверенным адаптером, либо удаляется; временные эксперименты не должны остаться в пользовательском плагине.

| Проверка | Что нужно доказать | Условие перехода дальше |
| --- | --- | --- |
| P0A Ввод | Удержание W, диагонали, key-up, русская раскладка; отсутствие текста и вызовов команд; бесконечный поворот; Esc/Alt+Tab | Повторяемый успешный запуск на 8.25, оба профиля мыши или доказанный путь второго |
| P0B Камера | Поза, FOV на трёх аспектах, snapshot, Esc и возврат из двухточечной/параллельной проекции | Возврат без дрейфа и изменения геометрии |
| P0C Превью | Другой camera frame без изменения рабочего вида, Shaded, нужный документ, блоки, базовый clipping | Живое превью работает; если off-screen не подходит, проверен отдельный родной preview view |
| P0D Данные | Запись и чтение plugin data, две записи, SaveAs, Undo/Redo изменения метаданных | Нет потери или дублирования записей после повторного открытия и Undo/Redo |
| P0E Опора | Сетка пола и вложенного блока, масштаб, mirrored transform, изменение единиц, локальный этаж | Подтверждены API извлечения и инвалидирования геометрии в 8.25 |

Артефакт P0 — короткий технический отчёт с версиями, результатами и выбранным путём для спорных API. Не требуется отдельное исследование всей RhinoCommon. Критичны только операции, от которых зависит проект.

Если P0A не пройден, нельзя маскировать проблему увеличением polling frequency или постоянно очищать командную строку после утечки символов. Нужно исправить место обработки ввода. Если P0C не пройден, нельзя незаметно заменить живой кадр статической картинкой.

## 3 P1 Надёжная базовая прогулка

Создать тонкий вертикальный срез: одна заданная точка, движение **По отметке**, WASD, мышь, height/FOV, Tab/Esc/Backspace, snapshot и полное освобождение ресурсов. После этого добавить полёт и режим правой кнопки.

Сначала добиться правильных единиц и ощущений, затем оформлять панель. На этом этапе уже обязательно проверяются RU/EN, Alt+Tab с зажатым W, другой viewport, закрытие окна и запуск команды Rhino. Нельзя отложить очистку ввода до конца проекта.

Результат этапа — работающая управляемая камера без установки через полноценный UI. Это инженерный прототип, ещё не готовый продукт.

## 4 P2 Установка и визуальная проверка

Добавить два шага выбора, черновик, временный силуэт, стрелку, сектор обзора и независимое превью. Согласовать исходный и целевой вид. Обработать пустую модель, наклонённый CPlane, недопустимую поверхность, установку с плана и отсутствие существующей перспективы.

Должен целиком проходить главный сценарий: кнопка → место → направление с превью → Enter → прогулка → Esc. На этом этапе ещё допустим только режим по отметке для геометрически сложных случаев, но UI обязан так его и называть.

## 5 P3 Наблюдатели и работа с документом

Добавить список записей, редактирование, дублирование, удаление, явное обновление после прогулки, сохранение в 3dm, корректный Undo/Redo, Named Views и настройки с областями действия.

Особенно проверить два документа, SaveAs, импорт геометрии, русские имена, повторную загрузку файла и смену единиц с масштабированием/без. Поддержать неизвестную версию данных без разрушительной перезаписи.

Результат — полноценный цикл сохранённого наблюдателя, а не только текущая сессия.

## 6 P4 Опора и архитектурная модель

Реализовать immutable геометрический снимок, пространственный индекс, поддержку вложенных блоков, локальный поиск пола, ступени, уклоны, остановку у края и сглаживание глаз. Добавить явный набор объектов/слоёв опоры. Инвалидировать кэш при изменении документа.

Проверить ходьбу по поверхности и возврат из полёта. Проверить, что подхватывание другого этажа и провал на несколько метров невозможны в предусмотренных случаях. Не добавлять столкновения со стенами в этот этап.

После P4 продукт обязан покрывать весь функциональный объём v1. До этого этапа сборка обозначается как предварительная.

## 7 P5 Качество и установка

Измерить плавность, задержку, перестройку кэша и утечки. Проверить поддержанные display modes, DPI, несколько мониторов, аварийные пути и длительную работу. Подготовить пакет Yak с платформой Windows и проверить установку на чистом пользовательском профиле Rhino 8.25.

Проверить удаление/отключение после штатного завершения: не остаются алиасы, таймеры, cursor capture, панели-призраки или сломанные файлы. Не обещать горячую выгрузку .NET-сборки без перезапуска Rhino, если хост её не поддерживает.

## 8 Разделение между несколькими исполнителями

Если владелец запускает несколько агентов Cursor, задачи разделяются по контрактам, а не по случайным экранам:

| Зона | Условие начала | Результат |
| --- | --- | --- |
| Математика и движение | Зафиксирован документ 02 | Детерминированное ядро и тесты единиц, базиса, времени |
| Rhino и ввод Windows | P0A/P0B | Управление сессией, CameraAdapter, InputBridge |
| Установка и интерфейс | Принят контракт Pose и SessionState | Панель, PlacementController, preview и conduit |
| Документ и опоры | P0D/P0E | Repository, сериализация, Undo, геометрический кэш |
| Интеграция и проверка | Каждый завершённый вертикальный срез | Реальный запуск в Rhino, дефекты и готовая сборка |

Ведущий исполнитель владеет общими DTO, состояниями, числами по умолчанию и контрактом событий. Несколько агентов не должны независимо создавать свои InputManager, единицы координат или camera math. Согласованные изменения контрактов отражаются в одном журнале решений.

## 9 Что должно лежать рядом с будущим кодом

Копия этого пакета, отчёт P0, журнал решений, карта выполненных приёмочных тестов и инструкция сборки. Не создавать внутренние документы ради количества: у каждого должна быть проверяемая функция.

Отчёт о тесте содержит ID, версию Rhino/Windows, тестовую сцену, шаги, фактическое поведение и итог Passed/Failed/Not run. Для интерактивных дефектов полезна короткая запись экрана. Успешная компиляция не закрывает ни один тест захвата, плавности или восстановления UI.

## 10 Граница готовности

Поставка считается готовой после P5 и прохождения всех обязательных проверок. Допускаемые ограничения перечислены в продуктовой спецификации, а не появляются задним числом для объяснения ошибок. Обязательные регрессии выполняются после изменения ввода, camera math, сериализации или геометрического кэша; декоративные правки панели не требуют бессмысленного полного перепрогона всех сцен.
